Локальний сайт у Docker-контейнері: завантажуєш фото нічного неба, а він сам знаходить зорі, визначає, куди дивилася камера (plate solving), підписує зорі, планети й Місяць і оцінює точність результату.

## 3. Чого навчило середовище ✅

- **pip:** `astropy`, `skyfield`, `tetra3rs` (каталог Gaia в комплекті) і `astroquery` ставляться без проблем.
- **apt:** `astrometry.net` і `astrometry-data-tycho2-10-19` (індекси на 60′–2000′, усього 36 МБ) теж ставляться. Для поля ~29° цих індексів достатньо.
- **astrometry.net + NumPy 2:** допоміжний скрипт `removelines` падає (`np.string_` прибрали). Обхід: `--no-remove-lines --uniformize 0`.
- **Стандартний пошук зір astrometry.net на цьому кадрі не спрацював**: заважають шум, рами вікна, підписи й агресивна обробка. Спрацював власний пошук:
  1. маска помаранчевих пікселів (R − B > 60), розширена на 6 px;
  2. віднімання фону медіанним фільтром 25×25;
  3. локальні максимуми у вікні 15×15 з порогом;
  4. центр ваги у вікні 7×7;
  5. відсіювання розмитих об'єктів за відношенням потоку в кільці до потоку в ядрі (< 1,5);
  6. 150 найяскравіших точок → `.xyls` → `solve-field`.
- У хмарному контейнері Claude закриті nova.astrometry.net, data.astrometry.net і JPL (de421, Horizons). Вдома під час збірки Docker-образу все це доступне.
- Точність вбудованої ефемериди astropy (`erfa.plan94`) для Юпітера: до 71″ по екліптичній довготі за 1800–2050 роки. Для точних результатів потрібна JPL-ефемерида (de421 або новіша).

### Що з'ясувалося під час написання бекенду ✅

- **DNG з Galaxy S22 — це лінійний DNG** (уже дебаєризований RGB, PhotometricInterpretation = LinearRaw), стиснутий **JPEG XL** (Compression = 52546). LibRaw (`rawpy`) його не відкриває, а `tifffile` + `imagecodecs` читають за ~0,5 с. Дані дуже темні: максимум 1241 з 65535, медіана неба 4. Тому прев'ю робиться розтягуванням яскравості з приглушеним кольором.
- **de421 не треба завантажувати з JPL:** вона лежить у пакеті `skyfield-data` на PyPI (MIT).
- **Каталог з назвами:** HYG 4.1 (Hipparcos + Yale + Gliese, власні назви МАС, позначення Байєра й Флемстіда). Лежить на GitHub, тож доступний і з хмари, і під час збірки. До 8m — 41 487 зір.
- **tetra3rs на оригінальному DNG** розв'язує з першої спроби за ~15 мс. Поле зору підказує EXIF: еквівалент 69 мм → ~28,2° (насправді 29,2°). Без підказки перебирає оцінки поля кроком ~1,25×, бо знаходить розв'язок лише при оцінці в межах приблизно ±30 %.
- **Підписи на JPG заважали tetra3rs:** 223 з 400 знайдених точок лежали на помаранчевих літерах. Допоміг загальний фільтр: на 8-бітних кадрах відкидаються насичено кольорові точки.
- **Юпітер з ореолом** мав завеликий потік у кільці, і його відкидало як розмиту пляму. Тепер протяжні об'єкти відкидаються лише тоді, коли вони видовжені або тьмяні, а яскраві круглі лишаються.
- **Після уточнення TAN-SIP на DNG:** 272 зорі, rms 56″ (~2 px при 26,8″/px), медіана 33″. Похибка не залежить від яскравості зорі.
- **Шибки вікна дають власне спотворення.** Середня шибка (там, де Юпітер) має розкид залишків 2,6 px, ліва й права — ~1,0–1,2 px. Скло — помітна частина похибки.
- **Юпітер проти de421** на точний час зі Львова: відхилення **~63″** (з вбудованою ефемеридою astropy було ~150″).

## 4. Конвеєр обробки

1. **Завантаження.** JPG або RAW/DNG (через `rawpy`). З EXIF беруться час, часовий пояс і GPS.
2. **Попередня обробка.** Для RAW — дебаєризація, без агресивного «покращення».
3. **Пошук зір.** Описаний вище алгоритм, з порогами під розмір кадру.
4. **Plate solving.** Спершу tetra3rs (мілісекунди), а якщо не вийде, astrometry.net. Якщо в EXIF є час і місце, розв'язувачу можна підказати, куди дивилася камера, але без них він теж справляється.
5. **WCS.** Формула «піксель ↔ небо», за потреби з поправкою на дисторсію (SIP).
6. **Підписи.**
   - зорі з каталогу (назви, позначення Байєра й Флемстіда, зоряна величина);
   - планети й Місяць через skyfield з JPL-ефемеридою, на точний час, із точки спостереження (топоцентрично; для Місяця це критично, бо паралакс ~1°);
   - зіставлення: найближча яскрава точка на кадрі ↔ розрахункове положення.
7. **Горизонтальна система координат.** Знаючи час і місце, порахувати висоту й азимут кожного пікселя, сітку висоти й азимута, лінію горизонту й рефракцію.
8. **Звіт про якість.** Скільки зір збіглося, похибка у ″, відхилення кожної підписаної планети від розрахунку.

## 5. Архітектура

```
docker run -p 127.0.0.1:8080:8080 -v ./data:/data astro-search
```
- Сайт відкривається на `localhost:8080`. Прив'язка до `127.0.0.1` означає, що з мережі до нього ніхто не достукається.
- Всередині Linux, тож однаково працює через Docker Desktop на Windows і в Debian-VM.

### Образ
- Основа — Debian.
- `apt`: `astrometry.net`, `astrometry-data-tycho2-10-19`.
- `pip`: `skyfield`, `tetra3rs`, `rawpy`, `aiohttp`, `numpy`, `scipy`, `astropy`, `pillow`.
- Під час збірки в образ завантажуються JPL-ефемерида і каталог зір. Після збірки контейнер працює повністю офлайн.

### Бекенд (Python, aiohttp)
| Модуль | Відповідає за |
|---|---|
| `ingest.py` | читання JPG/DNG, EXIF (час, часовий пояс, GPS) |
| `stars.py` | пошук центрів зір |
| `solve.py` | tetra3rs → astrometry.net, повертає WCS |
| `sky.py` | каталог, планети, Місяць, рефракція, висота й азимут |
| `server.py` | HTTP API і черга задач |

- **API:**
  - `POST /api/jobs` — завантажити фото (+ необов'язково час і координати), отримати `id`;
  - `GET /api/jobs/{id}` — статус і `result.json` (підписи в піксельних координатах, WCS, якість);
  - `GET /api/jobs/{id}/image` — зменшене прев'ю для показу.
- Задачі виконуються по одній у черзі, бо розв'язання вантажить процесор.
- Кожна задача зберігається в `/data/jobs/{id}/`: оригінал, `result.json`, проміжні файли.

### Фронтенд
- Vite + TypeScript без фреймворків. Залежності Node встановлюються в образ, а сама збірка запускається під час кожного старту контейнера (entrypoint), тож сторінку можна правити, змонтувавши `frontend/src`, без перезбирання образу.
- Фото, поверх нього SVG з підписами. Перемикачі шарів: зорі, планети, сузір'я, сітка висоти й азимута, горизонт, маска.
- Поле для координат на випадок, коли GPS в EXIF немає (за замовчуванням Львів).
- Клік по підпису показує інформацію про об'єкт: величину, відстань, відхилення від розрахунку.

## 6. Ідеї для оберненого розв'язання 💡

- **Дата за планетою** (уже працює, див. §2). Юпітер зазвичай зміщується на кілька кутових мінут за добу, тож дату можна визначити з точністю до доби, а то й кількох годин. Неоднозначності:
  - біля точок зупинки, коли планета змінює напрямок руху, швидкість ≈ 0;
  - петля попятного руху дає два кандидати;
  - 12-річний цикл Юпітера знімається, бо петлі щоразу лягають трохи інакше.
  - Кілька планет на одному кадрі звужують дату до одного варіанта.
- **Місце й час за зенітом.** Самі зорі не показують, де вертикаль. Але вертикальні лінії сцени (рами вікна, стіни) в перспективі сходяться в точці, яка і є зенітом. Координати зеніту на небі дають широту і місцевий зоряний час, а отже місце (якщо відомий час) або час (якщо відоме місце). При похибці зеніту 0,5–1° місце визначається з точністю ~50–100 км.
- **Місце за Місяцем.** Паралакс Місяця сягає ~1°, тож його положення серед зір залежить від точки на Землі.
- **Орієнтація телефона.** З WCS і часу видно, куди саме був спрямований телефон (азимут і висота) з точністю порядку 1′.

## 7. Оцінки точності

- Центри зір визначаються з точністю до частки пікселя; при 48″/px теоретично це одиниці–десятки ″.
- Реалістично для телефона через скло виходить ~1′.
- Помилка в часі на 1 с зсуває небо на ~15″ (обертання Землі), тож годинник телефона не лімітує.
- Паралакс Юпітера ~2″, тож точка спостереження для нього не важлива.
- Рефракція біля горизонту — десятки ″–хвилини, і її різниця між краями кадру частково поглинається масштабом WCS. Модель рефракції за відомих часу й місця прибирає залишок до одиниць ″.
- Похибка ефемериди: вбудована в astropy — до ~71″ для Юпітера, JPL — менше 1″.
- tetra3 (ESA) заявляє ~10″ для якісних камер з полем ~10°.
- ✅ **Дисторсія ширококутного об'єктива телефона.** Перевірено на окремому тестовому кадрі: Galaxy S24 Ultra, головна камера (23 мм екв.), JPG, 19.04.2025, Велика Ведмедиця майже в зеніті, поле 58×73°, 77″/px. З TAN-SIP 3-го порядку rms був 187″ (2,4 px), а відхилення — майже суто радіальні: +5 px біля центру, −3 px на середині радіуса, +5 px у кутах (поперек — лише ±0,7 px). Поліном 3-го степеня таку «хвилю» не описує, а `fit_wcs_from_points` із 4–5-го порядку погано обумовлений (поліном у сирих пікселях). Власна лінійна підгонка з радіальними членами r⁴, r⁶ і вибором моделі перехресною перевіркою: rms 46″, медіана 31″ (0,4 px), на зорях, яких підгонка не бачила, — 57″.
- ✅ **Кадри, де зорі лише в частині поля** (будинки, дерева). Стара підгонка (`fit_wcs_from_points`, SIP 3 при ≥60 зорях) у порожній частині кадру «розліталася» на сотні пікселів навіть без дисторсії; нова дає 0,1–2 px (половина кадру) і до ~10 px (одна чверть із сильною дисторсією). Ще одна вада, спільна для обох: поріг відсікання й радіус пошуку пар рахувалися від rms, хибні пари його роздували, і уточнення могло погіршити добре початкове наближення (вузьке поле, половина кадру: 0,7 px → 11 px). Тепер σ оцінюється за медіаною, а радіус не росте. Перевірка — `scripts/check_accuracy.py`.
- ❓ **tetra3rs на обрізаних JPEG із телефона** не розв'язує вирізки з кутів кадру (і стара, і нова версія): потоки зір на JPEG «сплющені» (найяскравіша точка лише вдвічі яскравіша за 400-ту), тож 80 найяскравіших точок — не обов'язково найяскравіші зорі.

## 8. Відкриті питання ❓

- ✅ **Лінії сузір'їв.** Узято d3-celestial (BSD 3-Clause, лінії за МАС) замість Stellarium, де ліцензію довелося б з'ясовувати. Усі 893 вершини збігаються із зорями HYG точніше за 0,005°.
- **Вгадування дати за планетами.** Вмикати завжди чи тільки тоді, коли в EXIF немає часу?
- **Ручне маскування.** Чи потрібен інструмент, яким можна замалювати рами вікна й засвітки?
- **Дисторсія об'єктива.** Калібрувати модель камери один раз (tetra3rs це вміє за кількома кадрами) і зберігати профіль телефона?
- **Каталог зір.** Яку граничну зоряну величину брати і звідки назви: власні назви МАС, Байєр, Флемстід?
- **Супутники.** Чи варто шукати треки МКС/Starlink за TLE? Для цього потрібен свіжий інтернет.

- **v4:** публічний сервіс: вхід через Discord, власники й ліміти, адмін-панель, публічні фото, nginx + docker compose + Cloudflare (див. §10).
- **Перша перевірка:** оригінальний DNG від 2024-11-01. Похибка має вийти помітно меншою за 1′ (JPG) і 2,5′ (Юпітер).
  - ✅ Виконано: rms по зорях ~56″, Юпітер ~63″ від розрахунку de421.
  - Межу тепер задає скло вікна, а не ефемерида.

## 10. Публічний сервіс (production) 💡

Мета: з локального інструмента зробити публічний сайт. Вхід лише через Discord, у кожного свої кадри й ліміти, є адмін-панель, а кадр за бажанням можна зробити публічним.

### Що в поточній версії не годиться для публічного доступу ❓

Стан коду на кінець жовтня 2026:

- **Авторизації немає взагалі.** `GET /api/jobs` віддає всі задачі всіх, будь-хто з id може завантажити оригінал (`/original`), видалити задачу (`DELETE`) чи змінити час і місце (`POST /observation`). Id — uuid4, тож вгадати його не можна, але список віддає їх усі.
- **Довільні файли до 300 МБ** розбираються бібліотеками на C (LibRaw, imagecodecs з JPEG XL, pillow-heif). Для чужих файлів це поверхня атаки: «бомби» розпакування, зависання, падіння. Падіння робочого процесу вже обробляється, але **загального таймауту задачі немає**: файл, на якому декодер зависне, назавжди зупинить чергу.
- **Одна черга й один робочий процес на всіх:** один користувач із сотнею файлів займе сервер для всіх інших.
- **Приватність.** В оригіналах лишається EXIF з GPS, а `result.json` містить точні координати місця зйомки й модель камери. Для публічних фото це витік адреси, тож місце треба огрублювати.
- Хешовані файли фронтенду (`/static/assets/*`) віддаються без заголовків кешування; `index.html` — з `no-cache` (так і треба).

### Вхід через Discord

- **Протокол:** OAuth2 authorization code flow зі scope `identify`. Достатньо Discord id, імені та аватарки, email не потрібен. Параметр `state` захищає від підробки входу.
- **Сесія:** cookie `HttpOnly`, `Secure`, `SameSite=Lax`, у браузері лише випадковий id сесії, а сама сесія — в базі. Для `POST`/`DELETE` додатково перевіряти `Origin`.
- **Перших адмінів** задати змінною оточення (`ASTRO_ADMIN_DISCORD_IDS`), далі ролі зберігати в базі.
- ❓ **Закрита бета:** пускати лише учасників свого Discord-сервера (scope `guilds.members.read` і перевірка членства).
- **У кожної задачі є власник.** Користувач бачить і змінює лише свої задачі, адмін — усі.

### Ліміти й квоти

- **На користувача:** кадрів за добу, задач у черзі одночасно, розмір файлу, загальний обсяг.
- **Черга справедлива** (по черзі між користувачами), а не «хто перший накидав».
- **Таймаут на всю задачу** і ліміти пам'яті/CPU робочого процесу.
- **Оригінали зберігати обмежений час** (напр. 7–30 днів, налаштовується), прев'ю й результат — доки кадр не видалили.
- **Видалення акаунта** прибирає всі файли користувача.

### Адмін-панель

- **Користувачі:** список, роль, бан, індивідуальні ліміти.
- **Кадри й файли:** усі задачі з фільтрами (власник, статус, розмір, видимість), видалити, обробити заново, змінити видимість, скільки місця займає.
- **Ліміти:** глобальні значення з розділу вище, змінюються без перезапуску.
- **Статистика:**
  - завантаження за день і активні користувачі;
  - частка розв'язаних кадрів і хто розв'язав (tetra3rs чи astrometry.net);
  - медіанний час обробки й довжина черги;
  - розподіл точності, популярні камери, зайняте місце.
- **Модерація публічних фото:** скарги, приховати кадр.

### Публічні фото

- **Видимість:** приватний (за замовчуванням), за посиланням, публічний (у галереї).
- **Галерея** з мініатюрами й фільтрами (сузір'я, планета, місяць, камера).
- **Публічна сторінка** `/p/<id>` з картинкою для попереднього перегляду (`og:image`): кадр із підписами, відрендерений на сервері. Тоді посилання в Discord і Telegram показуватимуть сам знімок.
- **Огрублене місце** в публічних даних (≈10 км або лише місто), без оригіналу й EXIF; час можна лишити.
- **Публічним може стати лише розв'язаний кадр.** Це дешевий фільтр проти сміття: фото, на якому не небо, не розв'яжеться.
- **Кнопка «поскаржитися»** відправляє кадр у чергу модерації.

### Зберігання файлів

Поточна версія зберігає на сервері все й без терміну. На кожен кадр у `/data/jobs/<id>/` лежать (розміри — для JPEG на 2,8 МБ):

| Файл | Розмір | Призначення |
|---|---|---|
| оригінал | 2,8 МБ (DNG — десятки МБ) | повторна обробка, завантаження власником |
| `preview.jpg` | ≈1,5 МБ: повна роздільність, JPEG q90 | показ у браузері |
| `result.json` | ≈0,5 МБ: точки, зорі, сітка, лінії | накладка, панелі |

Пропозиція:

- **Прев'ю** робити кількох розмірів: мініатюра ≈400 px і екранна версія ≈2560 px у WebP, а повну роздільність лишити тільки власникові. Після створення прев'ю **не змінюються**, лише видаляються, тож їх можна кешувати назавжди.
- **`result.json` змінюється**, коли власник уточнює час чи місце. Тому — номер версії в URL, і тоді кожна версія теж незмінна.
- **Оригінали** — лише тимчасово, див. «Ліміти й квоти».
- ❓ **Де зберігати:**
  - **на диску сервера** (том docker, nginx віддає файли сам): найпростіше, з цього й почати;
  - **у Cloudflare R2:** S3-сумісне сховище без плати за вихідний трафік, сервер тримає лише робочі файли обробки. Варто переходити, коли диска чи трафіку забракне.

### nginx, docker compose, Cloudflare

- **Контейнери** (усі в одному `compose.yml`):
  - `nginx` — віддає статичні файли й прев'ю;
  - `web` — API, aiohttp;
  - `worker` — обробка: окремий контейнер без мережі, з read-only файловою системою, обмеженнями пам'яті й CPU, його можна масштабувати;
  - `db`;
  - `cloudflared` — тунель, тоді назовні не відкрито жодного порту.
- **Черга задач — таблиця в базі** (`SELECT … FOR UPDATE SKIP LOCKED` у Postgres), без Redis.
- ❓ **База:** Postgres чи SQLite. SQLite простіша й на одному сервері впорається. Postgres зручніша для статистики й кількох worker-ів, а черга на `SKIP LOCKED` працює лише в ній. Рекомендація — Postgres.
- **nginx за Cloudflare:** справжню IP клієнта брати з `CF-Connecting-IP` (довіряючи лише адресам Cloudflare чи тунелю) і за нею обмежувати частоту запитів (`limit_req`); `client_max_body_size` — під ліміт завантаження.
- ❓ **Збірка фронтенду в production:** раз під час збірки образу, і nginx віддає готові файли. Поточна версія перезбирає фронтенд на кожному запуску контейнера — це зручно для розробки, але додає Node в робочий образ і секунди до старту.
- ❓ **Ліміт розміру запиту в Cloudflare:** на тарифах Free і Pro це 100 МБ (уточнити перед запуском). RAW на 100–300 МБ так не пройдуть. Варіанти: обмежити файли до 100 МБ, завантаження частинами, або завантаження браузером прямо в R2 за підписаним посиланням.

Кешування:

| Що | Змінюється? | Політика |
|---|---|---|
| `/static/assets/*` (хеш у назві) | ніколи | `public, max-age=31536000, immutable` (поточна версія заголовка не ставить) |
| `index.html` | з кожним релізом | `no-cache` (так і є) |
| прев'ю й мініатюри **публічних** кадрів | ніколи, лише видалення | `immutable` + очищення кешу Cloudflare через API при видаленні чи зміні видимості |
| прев'ю **приватних** кадрів | ніколи | `private`; nginx віддає лише після перевірки власника (`X-Accel-Redirect`); Cloudflare не кешує |
| `result.json` публічних кадрів | при зміні часу чи місця | версія в URL → `immutable` |
| API користувача (`/api/jobs`, сесія) | завжди | `no-store` |
| оригінали | — | не кешувати ніде, лише власникові |

Cloudflare за замовчуванням кешує лише файли зі статичними розширеннями й поважає `private`/`no-store`, тож правила кешу треба писати явно й лише для публічних шляхів.

### Безпека: чекліст перед запуском

- [ ] Вхід, власники, перевірка прав на кожному запиті (включно з `/preview`, `/original`, `/observation`).
- [ ] CSRF: `SameSite` cookie + перевірка `Origin`; заголовки `Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`.
- [ ] Робочий процес у пісочниці, таймаут задачі, межа пікселів зображення, менший ліміт розміру файлу.
- [ ] Ліміти запитів за справжньою IP (Cloudflare), квоти на користувача, справедлива черга.
- [ ] Огрублене місце й без EXIF у всьому публічному.
- [ ] Секрети (Discord client secret, ключ сесій) — лише через змінні оточення чи docker secrets.
- [ ] Резервні копії бази й тому з файлами; журнали без персональних даних.
- [ ] Політика приватності й «видалити мій акаунт».

### Порядок робіт

1. **Інфраструктура:** compose (nginx, web, worker, db, cloudflared), черга в базі, пісочниця й таймаут робочого процесу. Функції ті самі.
2. **Користувачі:** вхід через Discord, власники задач, сесії, CSRF, ліміти й квоти, термін зберігання оригіналів.
3. **Адмін-панель:** користувачі, файли, ліміти, статистика.
4. **Публічні фото:** видимість, галерея, `og:image`, огрублене місце, скарги, правила кешу Cloudflare й очищення кешу.

### Ще ідеї для публічної версії 💡

- **Discord-бот:** надсилаєш фото в канал — бот відповідає кадром із підписами. Застосунок у Discord однаково потрібен для входу, тож бот додається до нього.
- **Сповіщення в Discord**, коли кадр оброблено.
- **Гранична зоряна величина кадру** («видно зорі до 6,8m») і оцінка засвітки неба за фоном RAW. З публічних фото складається карта засвітки.
- **Досягнення й рейтинги:** найслабша зоря, перший Сатурн, усі 88 сузір'їв.
- **Карта публічних фото** (з огрубленим місцем).
- **Дата за планетами** (§6) — особливо для фото без EXIF.
- **Супутники за TLE** (§8).
- **Англійська версія** для ширшої аудиторії.
- **CI в GitHub Actions:** `pytest`, перевірка типів фронтенду, `check_accuracy.py` із закешованим каталогом; dependabot для залежностей Python і npm.
- **Моніторинг:** метрики (черга, час обробки, помилки), збір помилок, сповіщення, коли черга росте.
